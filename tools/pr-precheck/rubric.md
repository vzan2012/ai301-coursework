# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
| --- | --- | --- | --- |
| `diff-within-plan` | The diff's changed files and hunks, read against the plan-context block's Files list, its stated scope, its "not in scope" list, and any deviation or deferral note | Every changed file and every behavior-changing hunk serves the change the plan describes or a deviation the plan records, AND every deliverable the plan lists (code, tests, docs, changelog) appears in the diff or has its absence named in the plan's own deferral note. Fails on a hunk that adds, removes, or rewrites behavior or surface the plan never names (a new flag, option, rename, or rewrite of an untouched function), on anything inside the plan's "not in scope" list, or on a planned deliverable missing with no note. Hunks that change no behavior (whitespace, comments, dead code) are not judged here; `reviewable-diff` judges them | required |
| `description-matches-diff` | The PR description's concrete claims (what changed, "exactly as planned", "no other changes", "docs updated", "test added", "changelog entry"), each checked against the diff | Every concrete claim is visible in the diff, and no fidelity claim ("exactly", "only", "nothing else", "no functional changes outside X") is contradicted by any hunk. When the plan defers part of what the issue reports, the description states that deferral in its own text. Fails on a claim the diff does not contain (a docs update that is not in the diff), on a fidelity claim a hunk contradicts, or on a deferral the plan records that the description leaves out | required |
| `decisive-test-evidence` | The test-evidence section, read against the plan-context block's test plan and its repro-evidence steps | For every behavior the plan's test plan names (except one the plan explicitly defers), the package shows the plan's own repro scenario, on the code path the diff changes, with observable output after the fix and the before result stated or shown, or shows a new or changed test in the diff that asserts that behavior. Fails on "tested locally", "works on my machine", or "tests pass" with no named scenario or output, on evidence that only exercises a control or unchanged path, on a test that checks something other than the fix, or on a named failure mode of the plan's test plan that the evidence never exercises | required |
| `repo-checks-run` | The test-evidence section, read against the repo's own checks named in the plan's test plan and the repo-facts block (the suite, lint, typecheck) | At least one of the repo's own checks that covers the changed code is named and its outcome is visible (pass count, or the failures). Any named check not run is stated as not run, with the reason. Fails if no repo check is named, a check is named with no outcome ("ran the tests"), a failure goes unmentioned, or a check is skipped without saying so | required |
| `reviewable-diff` | The unified diff, line by line, and the commit list as a pointer to where scratch work may hide | No line in the diff is debris: debug output left in (including commented out), commented-out code, an unused function or import, a TODO or scratch note, or a hunk that changes no behavior and is not a planned deliverable (re-indent, reordered imports, re-printed identical lines). A comment that explains why the new code is written the way it is does not count as debris. Fails on any one debris line or hunk, however small | required |
| `repo-template-asks` | The repo-facts block's pull-request line (template sections, checklist, issue link, changelog or whatsnew ask, title format, tests ask), read against the title, description, and diff | Every ask the repo-facts block states is visibly met: each required section holds real content for this change (not empty and not boilerplate), the issue link is present, a stated changelog or whatsnew entry is in the diff, the title follows a stated format, and a checklist is filled in with each ticked item backed by something in the package. Passes when the block states no asks. Fails on any stated ask that is absent, empty, or ticked with nothing behind it | required |
| `ai-disclosure` | The repo-facts block's contribution-policy line (live mode: CONTRIBUTING.md, the PR template, and the course's requirement), read against the description | When a disclosure is asked for, the description states in its own text that AI was used, and names the tool and the extent when the policy asks for them. Passes when no policy asks. In live mode the course requires the disclosure for this PR, so it counts as asked. Fails when the ask exists and the description is silent, denies AI use, or says only "AI" with no sentence a maintainer could read | required |

## Verdict rule

Accept only if every check passes. Every check is `required`; there is no preferred check. Any check graded `fail` or `unclear` holds the package (reject): `unclear` is never free, and a PR that cannot be verified from the package is not ready to submit. A shortfall the plan defers and the description states honestly is not a failure by itself: it passes `diff-within-plan`, `description-matches-diff`, and `decisive-test-evidence` as scoped, and the package is accepted if every check passes. When the verdict is reject, name every check that failed or came back unclear in the readable summary, and quote the deciding fact for the first failing check in table order in the JSON.
