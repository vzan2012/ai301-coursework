# Evidence guide: where evidence lives in a PR package

## Plan fidelity (harness category: silent-drift)

Where it lives: in an eval bundle, the plan-context block holds the plan: its Files list, its scope sentence, its "Not in scope" list, and any note about a deviation or a deferred part. The candidate PR's Diff section shows what changed, and its Description shows what the PR claims. Live mode: `plan.md` in the working copy, including its Deviations section; the diff is `git diff main...HEAD` (three dots, against the repo's default branch) from the student's working copy; the claims are in the draft PR description.

What good looks like: every changed file and every behavior-changing hunk traces to something the plan states or a deviation it records, and every deliverable the plan lists is in the diff. Drift runs in both directions. More than the plan: pkg-03's description says "implements the posted plan exactly" while the diff adds a `truncate()` rewrite and a new `resolve_symlinks` option the plan scopes out. Less than the plan: pkg-17's plan promises a warning and a docs update, the diff holds only the warning, and the description says the docs now cover it. The description is a set of claims to test against the diff, never evidence in itself: pkg-03's commit list ("refactor", "feat") is a tell worth reading, but only the diff decides. An honest deferral is not drift: pkg-13's plan note defers `%VAR%` expansion and the description restates it, so the diff is complete as scoped.

## Test evidence (harness category: not-tested)

Where it lives: the candidate PR's Test evidence section, read against the plan-context block's test plan and the repro steps in its repro evidence. A test added in the diff counts as evidence only for what it asserts. Live mode: the student's captured terminal output for the repro, before and after, and for the repo's checks, plus the new tests in the diff.

What good looks like: the plan's own repro scenario is shown, on the changed code path, with output a stranger could read: what it printed before, what it prints after, and that the after matches the plan's expected result. pkg-02 shows the failing script printing `''` before and `'IMPORTANT OUTPUT\n'` after, and names `pytest tests/ -q` with "1462 passed, 12 skipped". "Tests pass" alone is never the deciding fact: pkg-04's "tested locally, colors work now, `cargo test` passes" never shows the plan's paged-output repro. Two traps: evidence that runs only a control (pkg-07 runs the single-file case that never broke; the plan's two-file repro is never re-run), and a test that covers something near the fix instead of the fix (pkg-14's test checks header casing, not the POST Content-Type repro). When the plan's test plan names two failure modes, both need evidence.

## Diff quality (harness category: unreviewable)

Where it lives: the unified diff in the candidate PR, read line by line, and the commit list as a pointer to where scratch work hides. Live mode: `git diff main...HEAD` and `git log main..HEAD --oneline`.

What good looks like: the fix is visible and nothing rides along that a reviewer would have to skip. The debris tells are specific: a debug print left in or commented out (`eprintln!("DBG...")`), commented-out code, an unused function or import (pkg-12's `_unused_buffer_probe`, pkg-15's `count_open_fds` behind `allow(dead_code)`), a TODO or scratch note, and hunks that change no behavior (re-indented blocks, reordered imports, identical lines re-printed). pkg-12 is the model case: the clamp is right and evidenced, and the diff still fails because of the commented-out debug line, the commented-out first attempt, the dead function, and the re-indent hunk. Commit messages like "wip" or "misc cleanups while debugging" say where to look; they are not the finding. A comment that explains why the new code is written that way is fine, and planned tests and changelog lines are deliverables, not debris.

## Standards and comms (harness category: standards-wall)

Where it lives: the repo-facts block. Its pull-request line states the template sections, checklist, issue-link, changelog or whatsnew, title format, and tests asks; its contribution-policy line states any AI-use disclosure rule. These are read against the candidate PR's title, description, and diff. Live mode: `.github/PULL_REQUEST_TEMPLATE.md` and `CONTRIBUTING.md` in the repo, plus the scope file's house rules; the course requires an AI-use disclosure on this PR even though the template has no section for it, so add the disclosure in the description.

What good looks like: each stated ask is visibly met with real content. pkg-01 is the template case: a solid fix with decisive evidence, but pandas' stated checklist is ignored, there is no `closes #` link, and the stated whatsnew entry is not in the diff. pkg-20 is the disclosure case: an excellent bounded fix, but ghostty's policy requires disclosing all AI use, naming the tool and the extent, and the description has none. A changelog entry the description claims but the diff lacks fails here too (pkg-12). A repo that states no asks and no AI policy passes both checks. Whether the description's claims match the diff is plan fidelity, above. The disclosure only needs to say that AI was used (and tool and extent if asked); how it is worded is the voice guide's business, not a grading condition.
